# Sonos Desk MQTT v1

Sonos Desk publishes what it discovers and observes, and accepts playback
commands through MQTT. The broker carries these messages; MQTTX is a client
for inspecting them. No Home service, controller assignments, or firmware are
required. The existing HTTP API and 800 × 480 PNG frame endpoint remain available.

## Reading the topic names

Every topic starts with:

```text
stonkworks/v1/sonos-desk/<instance>
```

`v1` is the protocol version. `<instance>` identifies one running Sonos Desk
installation, defaults to `main`, and is configurable. A development instance
named `dev` uses `stonkworks/v1/sonos-desk/dev`. Run only one service per instance
on a broker; two services with the same instance compete for the same MQTT
connection identity and topics.

In MQTTX, connect and subscribe to this to see a development instance:

```text
stonkworks/v1/sonos-desk/dev/#
```

`#` means all topics below that prefix. Use `stonkworks/#` to inspect all
Stonkworks instances. Subscribing does not change playback.

The reference below uses `<base>` for the instance prefix. Replace `<room_id>`
with a stable Sonos ID from the inventory, and `<client_id>` with the sending
application's identifier. Room names are labels and can change or repeat; they
are never used in MQTT command topic addresses. Examples use fictional IDs,
addresses, timestamps, and UUIDs, not household device assignments.

| Topic after `<base>/` | Publisher → consumer | Retained | MQTT expiry |
| --- | --- | --- | --- |
| `availability` | Sonos Desk → subscribers | Yes | None |
| `rooms` | Sonos Desk → subscribers | Yes | 90 seconds |
| `rooms/<room_id>/state` | Sonos Desk → subscribers | Yes | 90 seconds |
| `rooms/<room_id>/availability` | Sonos Desk → subscribers | Yes | 90 seconds |
| `rooms/<room_id>/command` | Control client → Sonos Desk | No | Required: 1–10 seconds |
| `clients/<client_id>/results` | Sonos Desk → requesting client | No | 30 seconds |

A retained message is the broker's latest saved value for a topic. A new
subscriber receives it immediately; it is not a history of all changes. Expiry
limits how long the broker can keep/deliver a message. It is an MQTT publish
property, not a JSON field.

Use MQTT 5 and QoS 1. QoS 1 can deliver duplicates; it does not confirm that a
speaker executed a command. JSON payloads are UTF-8 objects. Schemas live in
[sonos-desk.schema.json](sonos-desk.schema.json), under `$defs`. Response
objects may gain fields; command objects reject unknown fields.

## Fields shared across messages

| Field | Meaning |
| --- | --- |
| `service_session` | UUID created when the Sonos Desk process starts. Stays the same through broker reconnects; changes after process restart. Commands must target the current session. |
| `observed_at` | UTC RFC 3339 time when the inventory or room observation was made. Used to decide whether a saved snapshot is still current. |
| `request_id` | UUID generated by a control client for one user action. Appears in both that command and its result. |
| `client_id` | Application-level sender/result-routing ID, such as `desk-test`; matches `[A-Za-z0-9_-]{1,64}`. It is a payload field, not the broker account or the MQTT connection's client ID. |

Instance names use the same safe character pattern as application client IDs.
`service_session` is a process identity, not a user login or authentication
credential. Authorization comes from the broker account and topic permissions.

## 1. Service availability

**Topic:** `<base>/availability`
**Schema:** `availability`

Answers: **is this Sonos Desk MQTT interface connected and ready for commands?**

```json
{
  "status": "online",
  "service_session": "bb678ecb-e986-4c29-b0dd-7c4bdd79a1ae"
}
```

| Field | Meaning |
| --- | --- |
| `status` | `online` after the broker confirms the command subscription; `offline` when the service stops or its connection is lost. |
| `service_session` | The process session clients must use for new commands. |

This does not say that any speaker is reachable or playing. The service can
be online with zero rooms or with an unavailable speaker. Sonos Desk publishes
online after connecting/subscribing and offline on shutdown. An offline Last
Will asks the broker to publish offline after an unexpected disconnect;
detection is eventual, not instantaneous. There is no periodic availability
heartbeat, and the retained value does not expire. Check observation freshness
as well as availability before showing state as current.

## 2. Room inventory

**Topic:** `<base>/rooms`
**Schema:** `inventory`

Answers: **which rooms does this service know about, and how are they grouped?**

```json
{
  "service_session": "bb678ecb-e986-4c29-b0dd-7c4bdd79a1ae",
  "observed_at": "2026-10-16T20:00:00Z",
  "discovery": "ok",
  "rooms": [
    {
      "room": "Office",
      "room_id": "RINCON_00000000000101400",
      "ip": "192.0.2.11",
      "coordinator": "Kitchen",
      "coordinator_id": "RINCON_00000000000201400"
    }
  ]
}
```

| Field | Meaning |
| --- | --- |
| `discovery` | `ok` for a usable inventory read; `degraded` if discovery or inventory reading failed. |
| `rooms` | Array of known rooms. An empty array is valid. |
| `rooms[].room` | Friendly room name for display. |
| `rooms[].room_id` | Stable Sonos speaker ID; use this in room topics. |
| `rooms[].ip` | Current speaker IP address; informational, not its stable identity. |
| `rooms[].coordinator` | Friendly name of the group's playback coordinator. |
| `rooms[].coordinator_id` | Stable ID of that coordinator. |

The example shows one room entry from a grouped household. The full inventory
includes all discovered rooms, including the coordinator when discovered.
Publish on changes, after reconnect, and at least every 30 seconds while the
worker can refresh it. Underlying LAN discovery retains its existing
60-second cache, so publication does not imply a new network discovery.

Temporary discovery failure preserves the previous inventory and marks it
degraded. A failed metadata read preserves the last successful inventory's
observation time. A successful discovery with no rooms publishes `rooms: []`.
Consumers should stop using rooms removed from a fresh inventory. The service
clears retained state/availability for rooms it observes being removed; older
leftovers also expire.

## 3. Room state

**Topic:** `<base>/rooms/<room_id>/state`
**Schema:** `state`

Answers: **what is playing for this room, and what are its volume/mute settings?**

```json
{
  "service_session": "bb678ecb-e986-4c29-b0dd-7c4bdd79a1ae",
  "observed_at": "2026-10-16T20:00:03Z",
  "state": {
    "room": "Office",
    "room_id": "RINCON_00000000000101400",
    "coordinator": "Kitchen",
    "coordinator_id": "RINCON_00000000000201400",
    "title": "Example Song",
    "artist": "Example Artist",
    "album": "Example Album",
    "artwork_url": "http://192.0.2.12:1400/getaa?example",
    "playback_state": "PLAYING",
    "volume": 20,
    "mute": false,
    "duration": "0:03:21"
  }
}
```

The outer fields identify the process and observation time. Inside `state`:

| Field | Meaning |
| --- | --- |
| `room`, `room_id` | Selected room's display name and stable ID; the ID matches the topic. |
| `coordinator`, `coordinator_id` | Group playback coordinator's display name and stable ID. |
| `title`, `artist`, `album` | Current track/source metadata from the coordinator. Values can be empty when unavailable. |
| `artwork_url` | Speaker-supplied artwork URL, or an empty string. This is not a rendered display frame. |
| `playback_state` | Speaker transport state, such as `PLAYING`, `PAUSED_PLAYBACK`, or `TRANSITIONING`; passed through from Sonos. |
| `volume` | Selected room's volume, integer 0–100. |
| `mute` | Selected room's mute state, boolean. |
| `duration` | Speaker-supplied duration string, for example `0:03:21`; may be empty or source-dependent. |

Grouped rooms share playback/metadata through the coordinator, while volume
and mute remain specific to the selected room. These are the same state
fields returned by HTTP `/state`.

By default, each room is polled about every three seconds, without overlapping
reads. Publish when content changes and refresh successful unchanged state
about every 15 seconds. Slow speaker reads or queued commands can delay polls.
A failed read preserves the last successful state and its observation time;
it does not make that old value current again. Room availability reports the
failure separately. Reconnect triggers fresh reads before republishing state.

## 4. Room availability

**Topic:** `<base>/rooms/<room_id>/availability`
**Schema:** `room_availability`

Answers: **could the service read this particular room on its latest attempt?**

```json
{
  "service_session": "bb678ecb-e986-4c29-b0dd-7c4bdd79a1ae",
  "observed_at": "2026-10-16T20:00:03Z",
  "status": "online"
}
```

`online` means a room-state read succeeded. `offline` means it failed. This is
independent of whether playback is paused, stopped, or muted, and independent
of the service's own broker connection. One failed room does not mark every
other room offline. Publish changes and refresh the latest availability about
every 15 seconds while polling continues.

## 5. Command request

**Topic:** `<base>/rooms/<room_id>/command`
**Schema:** `command`

Answers: **what action does this client want performed on this room?**

```json
{
  "request_id": "36cdd095-21d8-48e0-bbe9-fd65fb715012",
  "client_id": "desk-test",
  "service_session": "bb678ecb-e986-4c29-b0dd-7c4bdd79a1ae",
  "command": "volume",
  "value": 20
}
```

| Field | Meaning |
| --- | --- |
| `request_id` | Fresh UUID for this user action; used to correlate the result and suppress duplicates. |
| `client_id` | Determines the result topic: `<base>/clients/desk-test/results` in this example. |
| `service_session` | Copy from the current online service availability message. Example UUIDs must be replaced. |
| `command` | One of the actions in the table below. |
| `value` | Required only for volume, relative volume, and mute; omit entirely for playback actions. |

The target room comes from the topic, not a `room` field in the JSON. Extra
fields are rejected. Room lookup remains ID-only even if inventory changes
between accepting and executing a command.

| `command` | `value` | Effect |
| --- | --- | --- |
| `play` | Omit | Start/resume playback through the coordinator. |
| `pause` | Omit | Pause through the coordinator. |
| `play_pause` | Omit | Read current playback state, then toggle play/pause. |
| `next` | Omit | Skip forward through the coordinator, if the source supports it. |
| `previous` | Omit | Skip backward through the coordinator, if supported. |
| `volume` | Integer 0–100 | Set the selected room's volume. |
| `volume_relative` | Integer -100–100 | Add to the selected room's volume, clamping the result to 0–100. |
| `mute` | Boolean | Set the selected room's mute state. |

Numbers must be JSON integers, not strings or booleans. Mute uses `true` or
`false`, not `1` or `0`. Playback commands reject even `"value": null`.

Publish with QoS 1, **Retain off**, and MQTT **Message Expiry Interval 1–10**
seconds. Sonos Desk requires a remaining expiry in that range on receipt and
checks the resulting deadline immediately before the speaker write, including
after waiting for other commands/HTTP calls. Expiry prevents starting an old
action; it cannot undo an action already sent to a speaker.

Retained commands are not executed. The service uses no persistent offline
command subscription. A process restart changes the session, causing requests
for the old session to be rejected.

## 6. Command result

**Topic:** `<base>/clients/<client_id>/results`
**Schema:** `result`

Answers: **what happened to my request?** Subscribe before sending the command.
Results for different rooms/actions can share this topic; match `request_id`.

A completed absolute-volume request:

```json
{
  "service_session": "bb678ecb-e986-4c29-b0dd-7c4bdd79a1ae",
  "client_id": "desk-test",
  "request_id": "36cdd095-21d8-48e0-bbe9-fd65fb715012",
  "room_id": "RINCON_00000000000101400",
  "completed_at": "2026-10-16T20:00:04Z",
  "status": "completed",
  "detail": "Command completed",
  "state": {
    "room": "Office",
    "room_id": "RINCON_00000000000101400",
    "coordinator": "Kitchen",
    "coordinator_id": "RINCON_00000000000201400",
    "title": "Example Song",
    "artist": "Example Artist",
    "album": "Example Album",
    "artwork_url": "http://192.0.2.12:1400/getaa?example",
    "playback_state": "PLAYING",
    "volume": 20,
    "mute": false,
    "duration": "0:03:21"
  }
}
```

| Field | Meaning |
| --- | --- |
| `service_session` | Session of the service reporting the result. A rejection of an old-session command reports the current service session. |
| `client_id`, `request_id` | Sender and action identifiers copied from the request. |
| `room_id` | Stable room ID from the command topic. |
| `completed_at` | UTC RFC 3339 time the result was recorded, including rejections and uncertain outcomes. |
| `status` | `completed`, `rejected`, or `uncertain`; see below. |
| `detail` | Human-readable explanation; clients should not branch on exact wording. |
| `state` | Included for `completed`: the selected room's newly read state, with the same fields as the nested room-state object above. |

| `status` | Meaning | Client response |
| --- | --- | --- |
| `completed` | Dispatch and the following state read succeeded. A `TRANSITIONING` state is valid and may settle later. | Use the returned state and subsequent observations. |
| `rejected` | Invalid input, stale session, expiry, unknown room, unsupported action, or overload. | Inspect `detail` and current configuration/state before deciding on another action. |
| `uncertain` | A speaker/backend failure means an attempted action may have taken effect, including a failed state read after sending. | Inspect state; do not automatically repeat the action. |

Example rejection:

```json
{
  "service_session": "bb678ecb-e986-4c29-b0dd-7c4bdd79a1ae",
  "client_id": "desk-test",
  "request_id": "36cdd095-21d8-48e0-bbe9-fd65fb715012",
  "room_id": "RINCON_00000000000101400",
  "completed_at": "2026-10-16T20:00:04Z",
  "status": "rejected",
  "detail": "Command expired before speaker dispatch"
}
```

Example uncertain outcome:

```json
{
  "service_session": "bb678ecb-e986-4c29-b0dd-7c4bdd79a1ae",
  "client_id": "desk-test",
  "request_id": "36cdd095-21d8-48e0-bbe9-fd65fb715012",
  "room_id": "RINCON_00000000000101400",
  "completed_at": "2026-10-16T20:00:04Z",
  "status": "uncertain",
  "detail": "Command sent but state refresh failed; read state before retrying"
}
```

These three examples illustrate alternative outcomes, not successive results
for one action. Results are non-retained, with 30-second MQTT expiry. A newly
connected MQTTX client normally sees no past results. Missing results do not
prove that a command failed; invalid/unroutable payloads can also be dropped
without a result. Malformed client/request IDs cannot safely receive replies.

## Freshness, duplicates, and display frames

Before showing state as current, require all of the following:

1. Service availability is online.
2. Inventory, room state, and room availability match that service session.
3. The room belongs to fresh inventory and its availability is online.
4. Inventory, state, and room availability observations are no older than
   45 seconds, allowing for ordinary clock skew.

Retained snapshots expire after 90 seconds, but consumers should mark them
stale at 45 seconds. An old retained online flag alone is not proof of current
speaker data. Topics are not an atomic snapshot, so brief mismatches during
updates are normal.

QoS 1 can duplicate messages. The service remembers accepted request IDs while
pending and for 60 seconds after completion, within a process session. An
identical duplicate returns its saved result without another speaker write;
a conflicting reuse of the same client/request ID is rejected. Duplicate
protection is bounded, not a permanent exactly-once ledger. Never reuse IDs
for new actions or renew an old action's expiry to force a retry.

Do not automatically retry actions, especially skip, toggle, or relative
volume, after an uncertain or missing result. Inspect state first. MQTT
transport acknowledgments confirm delivery at a transport boundary, not
speaker execution. A failed result publication never repeats the action.

Command payloads are limited to 4 KiB, with 16 queued actions and 1,024
pending/protected records. Overload rejects new work without evicting protected
records. Speaker reads and commands share serialization with HTTP.

Artwork URLs are metadata, not frame notifications. Rendered frames stay on
HTTP `/frame?room=<room_id>` and continue to support ETags; large PNGs are not
published through MQTT. See [the HTTP reference](../../docs/sonos-desk.md) for
render modes, conditional requests, and the cached `/mqtt/status` endpoint.

## Try with MQTTX

Connect MQTTX to your own broker, select **MQTT 5.0**, and use a separate
browser-client account. Subscribe to the base topic plus `/#`. Obtain the room
ID from `rooms` and the session UUID from online `availability`. Subscribe to
`clients/desk-test/results` before publishing a command.

Publish to `<base>/rooms/<room_id>/command` with QoS 1, **Retain off**, and
**Message Expiry Interval 10** in the MQTT 5 publish properties:

```json
{
  "request_id": "36cdd095-21d8-48e0-bbe9-fd65fb715012",
  "client_id": "desk-test",
  "service_session": "bb678ecb-e986-4c29-b0dd-7c4bdd79a1ae",
  "command": "volume",
  "value": 20
}
```

Replace the session with the current online service session and generate a
fresh request UUID for every new user action. The illustration's UUIDs must
not be reused for real actions. This command changes the selected room's
volume when sent to a live service. A rejected expiry request usually means
MQTT 5 publish properties were omitted; adding an expiry field inside the
JSON does not set MQTT message expiry.

## Single-command software client

After configuring `SONOS_MQTT_HOST`, `SONOS_MQTT_USERNAME`, and
`SONOS_MQTT_PASSWORD_FILE` (plus port/TLS settings when needed), run from the
repository root:

```sh
uv run --package sonos-desk python services/sonos-desk/examples/mqtt_client.py \
  --instance main --room-id '<stable-room-id>' --command volume --value 20
```

This sends an explicit action to the configured broker. `--value` uses JSON
syntax: `20`, `-1`, `true`, or `false`, with strict command-specific validation.
Omit it for playback commands. The client subscribes before sending, reads the
current session, sends once with ten-second expiry, and waits up to 15 seconds
for a result. It does not reconnect or retry the action. Exit codes: 0 completed,
2 rejected/invalid arguments, 3 uncertain, 4 no result, and 5 invalid broker
configuration. A timeout or disconnect can leave the action outcome uncertain.
